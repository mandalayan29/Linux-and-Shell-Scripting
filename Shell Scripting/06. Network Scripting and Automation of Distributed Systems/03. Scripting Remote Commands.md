# Testing `run-everywhere.sh`: A Full Walkthrough

## Goal of This Lesson

With `run-everywhere.sh` written, this lesson walks through **setting up the environment** and **thoroughly testing** every feature of the script — including error handling, quoting tricky arguments, and confirming exit statuses behave correctly, even when a server is unreachable.

---

## 1. Environment Setup Before Testing

Before the script can be tested, the admin server needs name resolution and passwordless SSH access to the other two servers — exactly as covered in setting up the network.

### Adding `/etc/hosts` Entries

```bash
echo "10.9.8.11 server01" | sudo tee -a /etc/hosts
echo "10.9.8.12 server02" | sudo tee -a /etc/hosts
```

### Verifying Name Resolution

```bash
ping -c 3 server01
ping -c 3 server02
```

Both should resolve to their correct IP addresses (`10.9.8.11` and `10.9.8.12`) and respond successfully.

### Setting Up SSH Key Authentication

Since this is a freshly created admin server, an SSH key pair needs to be generated:

```bash
ssh-keygen
```

Accept the default file location, and skip the passphrase — since the goal is to run remote commands **without** being prompted each time.

### Copying the Key to Each Server

```bash
ssh-copy-id server01
```

Accept the host fingerprint (`yes`), then enter the password (`vagrant` on this practice system).

```bash
ssh-copy-id server02
```

Same process for the second server.

### Verifying Passwordless Access

```bash
ssh server01 hostname
```

```
server01
```

```bash
ssh server02 hostname
```

```
server02
```

Both commands connect, execute remotely, return the result, and disconnect — with **no password prompt** — confirming the key-based authentication is working correctly.

## 2. Creating the Default Server List

```bash
cd /vagrant
echo "server01" > servers
echo "server02" >> servers
cat servers
```

- The **single** `>` on the first line **creates or overwrites** the file — if `servers` already existed, its old contents would be wiped out first.
- The **double** `>>` on the second line **appends** to the file, preserving the first line.

```
server01
server02
```

This matches the default `SERVER_LIST` path (`/vagrant/servers`) that the script expects.

## 8. Test 5: Dry Run Mode

```bash
./run-everywhere.sh -n hostname
```

Output:

```
DRYRUN: ssh -o ConnectTimeout=2 server01  hostname
DRYRUN: ssh -o ConnectTimeout=2 server02  hostname
```

### A Small Cosmetic Detail: Double Spaces

Look closely — there's an **extra space** between the server name and the command. This happens because the `SUDO` variable is empty (since `-s` wasn't used), but the **space characters around it in the command template are still there**:

```bash
SSH_COMMAND="ssh ${SSH_OPTIONS} ${SERVER} ${SUDO} ${COMMAND}"
```

When `${SUDO}` expands to nothing, the two spaces meant to surround it (one before, one after) both remain — producing a visible double space in the output. This is purely cosmetic and doesn't affect how the command actually executes, but it's worth understanding **why** it happens if you ever notice it in your own script output.

> **Why the naming choice `-n`?** This option was chosen to match a common convention seen in other Linux tools — for example, `rsync` also uses `-n` for its dry-run mode. You could have used something like `-d` instead, but following an existing convention can make your script feel more familiar to experienced users.

## 9. Test 6: Verbose Mode

```bash
./run-everywhere.sh -v uptime
```

Output:

```
Executing command on server01
 42 min,  0 users,  load average: 0.00, 0.00, 0.00
Executing command on server02
 41 min,  0 users,  load average: 0.00, 0.00, 0.00
```

With `-v`, each server's name is printed **immediately before** its command runs — making it clear which output belongs to which server.

> **Why this matters:** Without `-v`, you'd see just the raw `uptime` output stacked together, with no indication of which line came from which server — which becomes a real problem once you're running commands against many servers with similar-looking output.

## 15. Test 12: Handling Quoted Arguments (Nested Quotes)

### The Challenge

Suppose you want to create a second account, `test2`, with a **comment** of `"Test Two"` using `useradd -c`. Since the comment itself needs to be wrapped in quotes on the **remote** system, and the whole command **also** needs to be quoted so it travels through SSH as a single unit, we end up needing **quotes inside quotes**.

### The Trick: Use the Opposite Quote Type

To preserve one set of quotation marks literally, wrap them in the **opposite** type of quote.

### Demonstration

```bash
echo "'Test Two'"
```

```
'Test Two'
```

Here, the **outer** double quotes let the shell process the string normally, while the **inner** single quotes are preserved literally in the output, since single quotes don't have any special meaning when they appear *inside* double quotes.

> **Rule of thumb:** If you want single quotes to appear literally in your output, wrap the whole thing in double quotes. If you want double quotes to appear literally, wrap the whole thing in single quotes.

### Applying This to `run-everywhere.sh`

We need the comment `Test Two` to arrive at the remote `useradd -c` command **still wrapped in double quotes**, so it's treated as one argument (rather than two separate words, `Test` and `Two`).

### Always Test With a Dry Run First

Before running a command against every server — especially one that creates accounts or changes system state — it's wise to preview it with `-n` first, to catch quoting mistakes **before** they cause problems.

```bash
./run-everywhere.sh -n -s useradd -c "'Test Two'" test2
```

Output:

```
DRYRUN: ssh -o ConnectTimeout=2 server01 sudo useradd -c 'Test Two' test2
DRYRUN: ssh -o ConnectTimeout=2 server02 sudo useradd -c 'Test Two' test2
```

This confirms the comment will arrive on the remote system correctly wrapped in quotes, exactly as intended.

### Running It for Real

```bash
./run-everywhere.sh -s useradd -c "'Test Two'" test2
```

### Verifying With `-v`

```bash
./run-everywhere.sh -v id test2
```

```
Executing command on server01
uid=1002(test2) gid=1002(test2) groups=1002(test2)
Executing command on server02
uid=1002(test2) gid=1002(test2) groups=1002(test2)
```

### Double-Checking With `tail`

```bash
./run-everywhere.sh -v "tail -2 /etc/passwd"
```

```
Executing command on server01
test1:x:1001:1001::/home/test1:/bin/bash
test2:x:1002:1002:Test Two:/home/test2:/bin/bash
Executing command on server02
test1:x:1001:1001::/home/test1:/bin/bash
test2:x:1002:1002:Test Two:/home/test2:/bin/bash
```

Both accounts are confirmed on both servers — `test1` with no comment, and `test2` with the comment `Test Two` preserved correctly.

## 17. Test 14: A Server That's Unreachable

### Taking a Server Offline

From the **local physical machine** (outside any VM):

```bash
vagrant halt server02
```

> **Reminder:** Running `vagrant halt` **without** specifying a machine name halts **all** machines defined in the `Vagrantfile` — so it's important to target just `server02` here.

### Reconnecting and Re-Testing

```bash
vagrant ssh admin01
cd /vagrant
./run-everywhere.sh -v uptime
```

Output:

```
Executing command on server01
 51 min,  0 users,  load average: 0.00, 0.00, 0.00
Executing command on server02
ssh: connect to host server02 port 22: Connection timed out
Execution failed on server02
```

- `server01` responds normally.
- `server02` **times out** after the configured **2-second** `ConnectTimeout` — instead of hanging for a minute or more, exactly as intended.
- The script's own error message ("Execution failed on server02") confirms the failure was detected and reported.

### Checking the Exit Status

```bash
echo $?
```

Non-zero — confirming that when **any** server in the list can't be reached (or its command fails), the script correctly signals overall failure through its exit status, even though `server01` succeeded just fine.

> **Practical takeaway:** A non-zero exit status from this script is your signal to go review the output and figure out which specific server(s) had a problem — exactly the behavior the requirements called for.

## Anti-Patterns to Avoid

- **Don't** assume a "silent" command like `useradd` succeeded just because it produced no output — verify with a follow-up command (like `id`) run across the same server list.
- **Don't** run a command that modifies system state (like creating accounts) across every server without first previewing it with a dry run (`-n`) — especially when quoting is involved.
- **Don't** forget that nesting quotes requires **alternating quote types** — wrap the outer string in one type, and use the opposite type to preserve an inner literal quote.
- **Don't** skip testing failure scenarios (an invalid command, an unreachable server) — these confirm your script's error handling actually works, not just its "happy path."
- **Don't** assume a script "does nothing" just because there's no error on screen — always check the exit status (`$?`) as an additional confirmation, especially in scripts meant to be used in larger automation.

## Practice Questions

**Q1: Why does `useradd` produce no output when it successfully creates an account?**
A: Because by convention, many Linux commands only produce output when something goes wrong (an error); `useradd` stays silent on success.

**Q2: How can you confirm a "silent" command like `useradd` actually worked across all servers?**
A: Run a follow-up command (like `id USERNAME`) across the same server list and confirm the expected result appears on every server.

**Q3: Why does the dry-run output sometimes show a double space between the server name and the command?**
A: Because the `SUDO` variable is empty when `-s` isn't used, but the surrounding spaces in the command template remain, producing a visible (though harmless) double space.

**Q4: What rule allows you to preserve literal single quotes inside a double-quoted string (or vice versa)?**
A: Wrap the text in the opposite quote type — single quotes have no special meaning inside double quotes, and double quotes have no special meaning inside single quotes.

**Q5: Why is it recommended to use `-n` (dry run) before running a command that modifies system state across every server?**
A: To preview exactly what would be executed — including verifying that quoting is correct — before actually making changes on real (or in this case, test) servers.

**Q6: What happens to the script's exit status if the remote command itself doesn't exist (like `i-like-eggs`)?**
A: The script exits with a non-zero status, correctly signaling that something failed, even though SSH itself connected successfully.

**Q7: What happens when the script tries to reach a server that has been halted?**
A: SSH fails to connect and times out after the configured `ConnectTimeout` (2 seconds in this script), rather than hanging for a long time, and the script reports the failure and continues to the next server.

**Q8: Does the script stop immediately when it can't reach one server in the list?**
A: No — by design, it continues on to the remaining servers, and reports the failure for the unreachable one, so the entire list still gets processed in a single run.

**Q9: Why is it useful to check `$?` (the exit status) after running this script, not just look at the printed output?**
A: The exit status provides a reliable, scriptable way to detect that *something* failed somewhere in the run, which is especially useful when this script is called from within a larger automated workflow.

**Q10: Why was `-f` tested with both a valid custom list and an invalid, nonexistent path?**
A: To confirm both the "happy path" (the custom list is used correctly) and the error-handling path (a bad path is detected and reported cleanly) both work as intended.

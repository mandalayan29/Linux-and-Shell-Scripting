# Functions in Bash

## Goal of This Lesson

In this lesson, we will learn how to create and use **functions** in shell scripts. A function is a group of commands that you call using a single name — you can think of a function as a small script living inside your main script.

---

## 1. Why Use Functions

### Reason 1: Keep Your Code DRY

**DRY** stands for **"Don't Repeat Yourself."** It is a programming principle that says: write a block of code once, and reuse it wherever needed, instead of copying and pasting it multiple times.

**Benefits of DRY code:**

- Shorter scripts.
- A single place to change, test, troubleshoot, and document a task.
- Easier maintenance overall.

There is a joking counter-principle called **WET**, which stands for "Write Everything Twice," "We Enjoy Typing," or "Waste Everyone's Time." If you catch yourself copying and pasting the same code, it's time to turn that WET code into a function.

### Reason 2: Break Large Tasks Into Smaller Ones

Functions let you split a big task into smaller, focused pieces. You can zoom into one function that does just one small thing and make changes there, without touching the rest of the script. For example, inside a `case` statement, instead of writing a large block of code for each pattern, you can simply call a function that does the real work.

---

## 2. Two Ways to Define a Function

### Method 1: Using `function_name()`

```bash
function_name() {
    COMMANDS
}
```

### Method 2: Using the `function` Keyword

```bash
function function_name {
    COMMANDS
}
```

Both methods work exactly the same way — it's a matter of style preference.

### A Simple First Example

```bash
#!/bin/bash
# Demonstrate functions

log() {
    echo "You called the log function"
}

log
```

**Important rules:**

- Functions must be **defined before they are called**, since scripts run from top to bottom. This is why functions are usually placed near the top of the script.
- When a function is defined, its code is simply read into memory — it does **not run yet**. It only runs when you actually call it.
- To call a function, just write its name on its own line — **no parentheses** when calling it, even though you may have used `()` when defining it. (Some other programming languages use parentheses to call a function, but that syntax does not apply here.)

Run it:

```bash
chmod 755 luser-demo10.sh
./luser-demo10.sh
```

Output:

```
You called the log function
```

### The Alternate Style

```bash
function log {
    echo "You called the log function"
}

log
```

This produces the same output. Either style is valid — pick one and use it consistently.

## 3. Passing Data Into a Function: `local` and `${@}`

Let's make the `log` function display whatever message is passed to it.

```bash
log() {
    local MESSAGE="${@}"
    echo "${MESSAGE}"
}

log "Hello"
log "This is fun"
```

### The `local` Keyword

#### Syntax

```bash
local VARIABLE=VALUE
```

`local` makes a variable's scope limited to the function it is defined in. That means the variable only exists **inside that function** — trying to access it before or after the function call will show it as blank/unset.

> `local` can only be used **inside a function** — it has no meaning outside one.

### Global vs Local Variables

By default, all variables in Bash are **global** — accessible anywhere in the script, including inside every function.

- If you assign a variable inside a function **without** `local`, it becomes a global variable — but it won't actually exist until the function has been called at least once.
- It is a **best practice** to use `local` for variables inside functions. This avoids accidentally reusing the same variable name across different functions, which can cause hard-to-find bugs.
- Plenty of real-world scripts skip this practice and usually get away with it — but using unique variable names and `local` where appropriate keeps things safer.

### `${@}` Inside a Function

`${@}` should look familiar from the positional parameters lesson — it expands to all arguments, starting from `$1`.

Functions behave like a mini-script within your script:

| Inside a Function | Meaning |
|---|---|
| `${1}` | First argument passed to the **function** |
| `${2}` | Second argument passed to the **function** |
| `${@}` | All arguments passed to the **function** |
| `${0}` | Still the name of the overall **script** — not the function name |

> You would rarely need `${0}` inside a function anyway, since it always refers to the script, not the function.

### Testing

```bash
./luser-demo10.sh
```

```
Hello
This is fun
```

The function is called twice, each time with a different message, and each message is displayed.

## 4. Controlling Output With a `VERBOSE` Flag

Let's update the function to only print the message when a global variable `VERBOSE` is `true`.

```bash
log() {
    local MESSAGE="${@}"
    if [[ "${VERBOSE}" == true ]]; then
        echo "${MESSAGE}"
    fi
}

log "Hello"
VERBOSE=true
log "This is fun"
```

### Testing

```bash
./luser-demo10.sh
```

```
This is fun
```

**What happened:**

- When `log "Hello"` was called, `VERBOSE` was not yet set, so nothing was printed.
- After `VERBOSE=true` was set, `log "This is fun"` printed its message.

Without this function, you would need to repeat the `VERBOSE` check every time you wanted to conditionally display a message — leading to duplicated code throughout the script. This is exactly the kind of repetition functions help you avoid.

## 5. Global Variables: Pros, Cons, and a Practical Middle Ground

You may have heard that "global variables are evil" in formal programming training. In reality, what should be avoided are the **problems** that can arise from global variables — such as one function unexpectedly changing a value that another function depends on.

### Option A: Pass `VERBOSE` as an Argument (Avoids Global State)

```bash
log() {
    local VERBOSE="${1}"
    shift
    local MESSAGE="${@}"
    if [[ "${VERBOSE}" == true ]]; then
        echo "${MESSAGE}"
    fi
}

log true "Hello"
log true "This is fun"
```

**How this works:**

- `local VERBOSE="${1}"` captures the first argument (`true` or `false`) into a local variable.
- `shift` removes that first argument, so everything remaining becomes the message.
- Now every call to `log` must explicitly say whether it should be verbose.

### Option B: Use a Global `VERBOSE` Variable (Simpler, If Value Rarely Changes)

```bash
VERBOSITY=true

log() {
    local MESSAGE="${@}"
    if [[ "${VERBOSE}" == true ]]; then
        echo "${MESSAGE}"
    fi
}
```

> **Which is "correct"?** If a value like `VERBOSE` stays the same throughout the entire script, passing it as an argument every single call can feel repetitive without much benefit — using a global variable is a reasonable choice here. If the value is expected to **change** during the script (for example, differentiating info, warning, and critical log levels), passing it explicitly as an argument makes more sense.

> **Bottom line:** Both approaches are valid. Use whichever fits your situation, and make sure to test your script either way.

## 6. Protecting Global Variables With `readonly`

If you're worried about a function accidentally changing a global variable, you can lock that variable using the `readonly` built-in.

### Syntax

```bash
readonly VARIABLE=VALUE
```

or, assign first and mark it read-only afterward:

```bash
VARIABLE=VALUE
readonly VARIABLE
```

`readonly` makes a variable a constant — it **cannot be changed** for the rest of the script's execution, whether the attempted change happens inside or outside a function.

### Example

```bash
readonly VERBOSE=true
```

Now `VERBOSE` is locked in as `true` and cannot be accidentally modified anywhere in the script.

## 7. Sending Messages to the System Log With `logger`

So far, our `log` function only displays messages to the screen (when `VERBOSE` is true). Let's also make it record messages permanently using the `logger` command.

### Syntax

```bash
logger [OPTION]... [MESSAGE]
```

| Option | Meaning |
|---|---|
| `-t TAG` | Tags the log message, typically with the name of the program/script writing it |

`logger` is a program (not a shell built-in), so use `man logger` for full details.

```bash
man logger
```

By default, on CentOS/RHEL systems, `logger` messages are written to `/var/log/messages`.

### Example: Basic Usage

```bash
logger "Hello from the command line"
```

```bash
sudo tail /var/log/messages
```

The last line of the log file shows your message. The log format is:

```
TIMESTAMP  HOSTNAME  TAG: MESSAGE
```

Since we didn't provide a tag, the current username was used instead.

### Example: With a Tag

```bash
logger -t my-script "Tagging on"
```

Now the log entry's tag reads `my-script`, making it clear which script or program generated the message.

> **Security note:** Syslog can be configured to send messages to a **centralized remote server**. This is a good security practice — if an attacker gains root access to one system, logs stored only locally could be altered or deleted. Sending logs to a separate, remote system makes tampering much harder. (Configuring centralized syslog is beyond this lesson's scope.)

### Adding `logger` to the `log` Function

```bash
log() {
    local MESSAGE="${@}"
    logger -t luser-demo10.sh "${MESSAGE}"
    if [[ "${VERBOSE}" == true ]]; then
        echo "${MESSAGE}"
    fi
}
```

Now, **regardless of whether `VERBOSE` is true**, every message passed to `log` is always recorded in the system log — but it is only shown on screen when `VERBOSE` is `true`.

### Testing With Verbose On and Off

```bash
VERBOSE=true
```

```bash
./luser-demo10.sh
```

Messages appear on screen **and** in the log file.

```bash
sudo tail /var/log/messages
```

```bash
VERBOSE=false
```

```bash
./luser-demo10.sh
```

No output appears on screen, but the messages are still recorded in the log file:

```bash
sudo tail /var/log/messages
```

```
Hello
This is fun
```

### Documenting a Function

Just like scripts benefit from a header comment, functions benefit from a short comment describing what they do:

```bash
# This function sends a message to syslog
# and to standard output if VERBOSE is true
log() {
    local MESSAGE="${@}"
    logger -t luser-demo10.sh "${MESSAGE}"
    if [[ "${VERBOSE}" == true ]]; then
        echo "${MESSAGE}"
    fi
}
```

> Some people also document any global variables the function relies on, the arguments it accepts, and what it returns — this becomes especially useful once you start using `return` values (covered later in this lesson).

> **Reminder:** Functions must be defined before they're used. Keep all function definitions near the top of your script. The only things that generally make sense to place *before* your functions are constant global variables and sourcing external script libraries.

## 8. Building a Second Function: `backup_file`

### The Goal

Before a script modifies a file, it's wise to make a backup copy first — that way, if something goes wrong, the original data can be restored.

### Choosing Where to Store Backups

| Directory | Behavior |
|---|---|
| `/tmp` | Not guaranteed to survive a reboot; files may be cleared automatically (e.g. every 10 days on some CentOS 7 systems) |
| `/var/tmp` | Survives reboots; files typically cleared less often (e.g. every 30 days on some CentOS 7 systems) |

Since we don't want to lose a backup just because the system reboots, `/var/tmp` is the better choice here.

### Building the Function

```bash
# This function creates a timestamped backup copy of a file in /var/tmp
backup_file() {
    local FILE="${1}"

    if [[ -e "${FILE}" ]]; then
        local FILE_NAME=$(basename "${FILE}")
        local TIMESTAMP=$(date +%F-%s%N)
        local BACKUP_FILE="/var/tmp/${FILE_NAME}.${TIMESTAMP}"

        log "Backing up ${FILE} to ${BACKUP_FILE}"
        cp -p "${FILE}" "${BACKUP_FILE}"
    else
        log "${FILE} does not exist. Cannot create backup."
        return 1
    fi
}
```

### Explaining Each Piece

- **`local FILE="${1}"`** — captures the file to back up (the first argument passed to the function).
- **`[[ -e "${FILE}" ]]`** — checks that the file actually exists before trying to back it up.
- **`basename "${FILE}"`** — strips the directory path, leaving just the file name, since the backup will live in a different directory (`/var/tmp`) anyway.
- **`date +%F-%s%N`** — builds a timestamp for the backup file name:

  | Format | Meaning |
  |---|---|
  | `%F` | "Full date" — displays the date as `YYYY-MM-DD`, which sorts nicely by date |
  | `%s` | Seconds since the Epoch |
  | `%N` | Nanoseconds — helps avoid filename collisions if the function is called multiple times on the same day |

  > Alternatives for uniqueness could include `$RANDOM`, `$BASHPID`, or `$$` (which expands to the process ID of the current script).

- **`log "..."`** — calls our earlier `log` function to record what's about to happen. This shows functions calling other functions.
- **`cp -p`** — copies the file. The `-p` (preserve) option keeps the original file's permissions, ownership, and **timestamps**.

  > **Why preserve timestamps?** Since a backup's contents haven't changed from the original, it makes sense to keep its original timestamp rather than showing today's date — that way, if you restore the file later, its history is preserved. Without `-p`, the copy would show today's date and time instead of the original.

- **`return 1`** — if the file doesn't exist, the function can't do its job, so it returns a non-zero (failure) exit status.

### Testing

```bash
VERBOSE=true
backup_file /etc/passwd
```

Output shows both the `log` message about the backup and confirms it ran successfully. Checking the log file:

```bash
sudo tail /var/log/messages
```

The backup event is recorded there too, giving you a record of exactly what happened and when.

```bash
ls -l /var/tmp/
```

Shows the new backup file, with a name like:

```
passwd.2026-09-04-1234567890123456789
```

### Verifying the `-p` Option's Effect

Without `-p`:

```bash
cp /etc/passwd /var/tmp/
ls -l /var/tmp/passwd /etc/passwd
```

The copy in `/var/tmp` shows **today's date**, while the original `/etc/passwd` still shows its **original, older date** — proving that without `-p`, the timestamp is not preserved.

## 9. Function Return Values (Exit Status)

Just like any other command, a function returns an **exit status**. By default, this is the exit status of the **last command executed inside the function**.

- If `backup_file` successfully copies the file, its exit status comes from `cp` — `0` if successful, non-zero if `cp` failed.
- If the file didn't exist, we explicitly `return 1` to signal failure.

### Checking a Function's Return Status

```bash
backup_file /etc/passwd

if [[ $? -eq 0 ]]; then
    log "File backup succeeded"
else
    log "File backup failed"
    exit 1
fi
```

### `return` vs `exit` — A Critical Difference

| Command | Effect |
|---|---|
| `return [N]` | Ends the **current function** and sets its exit status. Use this **inside** functions. |
| `exit [N]` | Ends the **entire script**, no matter where it's called — even from inside a function. |

> **Rule of thumb:** Inside a function, always use `return`, never `exit` — unless you truly intend to stop the whole script right then and there.

### Testing

```bash
./luser-demo10.sh
```

Output confirms:

```
File backup succeeded
```

```bash
sudo tail /var/log/messages
```

Shows the "File backup succeeded" message logged as well.

> In practice, since you'd want to check the success of a backup **every time** it happens, it usually makes more sense to move this success/failure check **inside** the `backup_file` function itself, rather than repeating it after every call.

## 10. Optional: Splitting Into Multiple Functions (Advanced Pattern)

If you wanted to separate concerns even further, you could split the work into three functions:

1. `perform_backup` — does the actual copying.
2. `check_backup` — verifies whether the backup succeeded.
3. `backup_file` — a "wrapper" function that calls both of the above, in order.

```bash
backup_file() {
    perform_backup "${@}"
    check_backup
}
```

This is a form of over-engineering for a simple case like this one, but it shows how functions can call other functions to build up more complex behavior from small, focused pieces.

> **Note:** If `perform_backup` and `check_backup` are not actually defined, calling `backup_file` will fail with "command not found" errors for each missing function — a good reminder that every function you call must be defined somewhere in your script (or already loaded into the shell).

## 11. Defining Functions Directly at the Command Line

Just like a script automates what you can already do interactively, you can define and test a function directly in your terminal session, without putting it in a script file first.

### Checking a Function's Definition

```bash
type -a backup_file
```

Output:

```
backup_file is a function
backup_file ()
{
    ...
}
```

This shows that `backup_file` is recognized as a function, and even prints out its full definition — useful for quickly checking or reviewing functions you've already defined in your current shell session.

## Anti-Patterns to Avoid

- **Don't** call a function before it has been defined — scripts run top to bottom, so undefined functions will fail with "command not found."
- **Don't** use parentheses (`()`) when **calling** a function — only use them (optionally) when **defining** one.
- **Don't** forget the `local` keyword for variables inside functions — omitting it makes them global, which can cause naming collisions and hard-to-trace bugs.
- **Don't** use `exit` inside a function unless you actually intend to stop the entire script — use `return` instead.
- **Don't** repeat the same block of logic (like a verbose-mode check) throughout your script — wrap it in a function instead, following the DRY principle.
- **Don't** forget `cp -p` when the goal is to preserve a file's original timestamp during a backup.

## Practice Questions

**Q1: What does DRY stand for, and why does it matter?**
A: "Don't Repeat Yourself." It matters because repeated code is harder to maintain — a bug or change has to be fixed in multiple places instead of one.

**Q2: What are the two ways to define a function in Bash?**
A: `function_name() { ... }` or `function function_name { ... }` (without parentheses).

**Q3: Do you use parentheses when calling a function?**
A: No. You only use the function's name to call it — parentheses are only used (optionally) at definition time.

**Q4: What does the `local` keyword do, and where can it be used?**
A: It limits a variable's scope to the function it is declared in. It can only be used inside a function.

**Q5: Inside a function, what does `${1}` refer to?**
A: The first argument passed to the **function** — not to the overall script.

**Q6: What does `${0}` refer to when used inside a function?**
A: It still refers to the name of the overall script, not the function.

**Q7: What is the difference between `return` and `exit`?**
A: `return` ends the current function and sets its exit status. `exit` ends the entire script, no matter where it is called from — even inside a function.

**Q8: What does the `readonly` built-in do?**
A: It marks a variable as unchangeable (a constant) for the rest of the script's execution, preventing it from being modified anywhere, including inside functions.

**Q9: What does the `-p` option to `cp` do, and why is it useful for backups?**
A: It preserves the file's permissions, ownership, and timestamps. It's useful for backups because the backup's contents are unchanged from the original, so keeping the original timestamp makes sense.

**Q10: Why must functions be defined before they are called in a script?**
A: Because scripts execute from top to bottom, and Bash needs to have already read a function's definition into memory before it can find and run it when called.

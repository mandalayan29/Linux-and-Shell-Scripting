## 2. Creating Your First Shell Script

To create and edit a file using Vim:

**Syntax:**
```
vim <filename>
```

**Example:**
```
vim luser-demo01.sh
```

### A Note on File Names

File names in shell scripting **do not matter** for execution. The `.sh` extension is just a **convention** (a common habit), not a rule.

- On Windows, `.exe` tells the system "this is a program."
- On Linux, there is no such rule. You could name a script `luser-demo01.sh`, `luser-demo01`, `Bob`, or `Fred` — it will still work as a script, as long as it has execute permission (explained later).

## 3. The Shebang Line

The very first line of a shell script should look like this:

```
#!/bin/bash
```

This is called a **shebang**.

### Where does the name "shebang" come from?

- The `#` symbol is sometimes called a **"sharp"** (it looks like the sharp symbol in music).
- The `!` symbol is sometimes called a **"bang"**.
- Put "sharp" and "bang" together, shorten it a little, and you get **"shebang."**

### What does the shebang do?

The shebang tells the system **which program should run the commands** in the script.

```
#!/bin/bash        → commands are run by the Bash shell
#!/usr/bin/python  → commands are run by Python (makes it a Python script)
#!/usr/bin/ruby    → commands are run by Ruby (makes it a Ruby script)
```

When you execute the script, the interpreter listed in the shebang (for example `/bin/bash`) runs, and your script's filename is passed to it. That interpreter then reads and runs every command in the file.

### What happens if you don't include a shebang?

If you don't specify an interpreter, the script will run using **whatever shell you are currently using**. This can cause errors if:

- Your script uses Bash-specific features, and
- The person running it is using a different shell (like `csh`).

**Best Practice:** Always start your script with a shebang. This is especially important when working in a team, since you can't control what shell your teammates use.

## 4. Comments

A **comment** is a line that starts with `#` (except the very first line, which is the special shebang line).

```
# This script displays various information to the screen
```

### Key Points about Comments:

- Comments are **not executed** by the shell.
- They exist only for **humans** to read.
- Use comments to explain what your script does, especially at the top of the file.
- This helps you (or someone else) understand the script months or years later.

**Example:**
```bash
#!/bin/bash
# This script just displays various information to the screen

# Display the text hello
echo 'hello'
```

## 5. Making a Script Executable (File Permissions)

Having the right file name is not enough. A script also needs the **execute permission** before it can run.

### Quick Review of File Permissions

When you run `ls -l`, you will see permission characters like this:

```
-rw-r--r--
```

This is broken into **three groups of three characters**:

| Position | Meaning | Example |
|---|---|---|
| First 3 characters | Owner's permissions | `rw-` |
| Next 3 characters | Group's permissions | `r--` |
| Last 3 characters | Everyone else's permissions | `r--` |

Each permission has a value:

| Permission | Letter | Value |
|---|---|---|
| Read | `r` | 4 |
| Write | `w` | 2 |
| Execute | `x` | 1 |

### The `chmod` Command

**Syntax:**
```
chmod <permission-number> <filename>
```

**Options (permission calculation):**
- Owner permission = sum of (read=4, write=2, execute=1)
- Group permission = sum of (read=4, write=2, execute=1)
- Others permission = sum of (read=4, write=2, execute=1)

**Example:**
```
chmod 755 luser-demo01.sh
```

How `755` is calculated:

```
7 = 4 (read) + 2 (write) + 1 (execute)   → Owner: read, write, execute
5 = 4 (read) + 1 (execute)               → Group: read, execute
5 = 4 (read) + 1 (execute)               → Others: read, execute
```

**Recommended default permission for scripts: `755`**
This gives you (the owner) full control, while others can read and run the script but not edit it.

> **Note:** If you don't have read permission on a file, you also can't execute it — the interpreter needs to be able to read the commands first.

## 6. Running a Shell Script

**Syntax:**
```
./<filename>
```

**Example:**
```
./luser-demo01.sh
```

### Understanding the `./` Part

- `.` (single dot) means **"this current directory."**
- `..` (double dot) means **"the parent directory"** (one level up).
- `/` is the **directory separator**.

So `./luser-demo01.sh` means: *"run the file named `luser-demo01.sh` that is located in this current directory."*

This is the same as using the full path:
```
/vagrant/luser-demo01.sh
```

### What happens if the execute bit is missing?

If you try to run a script without execute permission:

```
./blah.sh
```

You will see:
```
Permission denied
```

**Fix:** Run `chmod 755 blah.sh` first, then try again.

## 7. Shell Builtins vs External Commands

### What is a Shell Builtin?

A **shell builtin** is a command that is built directly into the shell (like Bash). It does not need to load any external program to run — it's simply part of the shell itself.

### Checking if a Command is a Builtin

**Syntax:**
```
type <command>
type -a <command>
```

- `type <command>` → shows what will run when you type that command.
- `type -a <command>` → shows **all** locations/types of that command, in the order they would run.

**Example:**
```
type echo
```
Output:
```
echo is a shell builtin
```

**Example (checking a non-builtin):**
```
type -a uptime
```
Output:
```
uptime is /usr/bin/uptime
```
This tells us `uptime` is an **external program**, not a shell builtin.

### Why Use Shell Builtins When Possible?

1. **Faster** – no need to load an external program.
2. **More portable** – an external command (like `echo`) might be located at `/bin/echo` on one system and `/usr/bin/echo` on another. A builtin avoids this problem entirely, since it's always part of the shell.

### Getting Help

| Type of Command | How to Get Help |
|---|---|
| Shell builtin (e.g. `echo`) | `help echo` |
| External command (e.g. `uptime`) | `man uptime` |

**Example:**
```
help echo | less
```
This pipes the help output to `less` (a pager) so you can scroll through it. Press `q` to quit `less` or `man`.

> Trying `help uptime` won't work, because `uptime` is not a builtin. Similarly, `man echo` won't give Bash-specific builtin help — use `man bash` for that.

## 8. Variables

### What is a Variable?

A variable is a **named storage location** that holds a value. Think of it as a name-value pair.

**Syntax to create a variable:**
```
VARIABLE_NAME='value'
```

**Example:**
```bash
WORD='script'
```

### Important Rules for Creating Variables

1. **No space** around the `=` sign.
   ```bash
   WORD='script'      # Correct
   WORD = 'script'     # Wrong — this will cause an error
   ```
2. You do **not** need to declare a type (like string or integer) — just assign a value.
3. Variable names can contain **letters, digits, and underscores**, and must **start with a letter or underscore**.

| Variable Name | Valid? | Reason |
|---|---|---|
| `word` | ✅ Yes | Starts with a letter |
| `word1` | ✅ Yes | Starts with a letter |
| `_word` | ✅ Yes | Starts with an underscore |
| `3word` | ❌ No | Cannot start with a digit |
| `a-word` | ❌ No | Dashes are not allowed |
| `e@mail` | ❌ No | Special characters like `@` are not allowed |

4. **Naming convention:** By convention (not a strict rule), variable names are written in **UPPERCASE**. This makes them easy to spot in a script. Bash will still work fine with lowercase variable names, but uppercase is the recommended best practice.

> **Tip:** Use descriptive variable names. Avoid short, unclear names — it makes scripts much easier to read for you and others later.

---

## 9. Using (Reading) a Variable

To read the value stored in a variable, put a `$` sign before its name.

**Syntax:**
```
echo "$VARIABLE_NAME"
```

**Example:**
```bash
WORD='script'
echo "$WORD"
```
**Output:**
```
script
```

---

## 10. Single Quotes vs Double Quotes

This is one of the most important concepts for variables.

| Quote Type | Behavior |
|---|---|
| Single quotes `' '` | Variables are **not expanded**. Displays exactly what you typed. |
| Double quotes `" "` | Variables **are expanded** into their value. |

**Example:**
```bash
WORD='script'

echo '$WORD'     # Output: $WORD   (not expanded)
echo "$WORD"     # Output: script  (expanded)
```

> This rule about quotes applies to more than just `echo` — it applies across Bash generally.

## 11. Combining Variables with Text

You can mix variables with regular text.

**Example:**
```bash
WORD='script'
echo "This is a $WORD"
```
**Output:**
```
This is a script
```

### Appending Text Directly After a Variable

If you want to add text **immediately** after a variable (with no space), you must use **curly braces** `{}` around the variable name.

**Syntax:**
```
"${VARIABLE_NAME}extra_text"
```

**Correct Example:**
```bash
WORD='script'
echo "${WORD}ing is fun"
```
**Output:**
```
scripting is fun
```

**Incorrect Example (what NOT to do):**
```bash
WORD='script'
echo "$WORDing is fun"
```
**Output:**
```
 is fun
```
This fails because Bash thinks the variable name is `WORDing` (which doesn't exist), so it expands to nothing.

### Why This Happens

```
"$WORD" + "ing"   →  Bash cannot tell where the variable name ends
                      and the extra text begins.

"${WORD}" + "ing" →  The curly braces clearly mark where the
                      variable name ends, so "ing" is treated
                      as separate text.
```

---

## 12. Reassigning Variables

You can change the value stored in a variable at any point in the script. This is called **reassignment**. Since scripts run from **top to bottom**, any command after the reassignment will use the **new value**.

**Example:**
```bash
WORD='script'
ENDING='ed'
echo "${WORD}${ENDING} is fun"   # Output: scripted is fun

ENDING='ing'
echo "${WORD} ${ENDING} is fun"  # Output: script ing is fun
```

## Summary

Here is what you learned in this tutorial:

- **File names don't matter** for execution — the `.sh` extension is just a convention. What actually matters is the **execute permission**.
- **Shebang (`#!/bin/bash`)** — the first line of a script that tells the system which interpreter should run the script.
- **Comments (`#`)** — lines meant only for humans; they are not executed (except the shebang line, which is a special case).
- **File Permissions (`chmod 755`)** — needed to make a script runnable. Read = 4, Write = 2, Execute = 1.
- **Running a script** — use `./scriptname` or the full path.
- **Shell Builtins** — commands built into the shell (like `echo`), faster and more portable than external commands. Use `type` to check, `help` for documentation on builtins, and `man` for external commands.
- **Variables** — name-value pairs. Use `$` to read a value, and `${}` when you need to combine a variable directly with more text.
- **Single quotes** prevent variable expansion; **double quotes** allow it.

### Quick Command Reference

| Command | Purpose |
|---|---|
| `vim <file>` | Create/edit a file |
| `chmod 755 <file>` | Make a file executable |
| `./<file>` | Run a script in the current directory |
| `type <command>` | Check if a command is a builtin |
| `type -a <command>` | Show all versions/locations of a command |
| `help <builtin>` | Get help for a shell builtin |
| `man <command>` | Get help for an external command |
| `echo "text"` | Display text (with variable expansion) |
| `echo 'text'` | Display text (no variable expansion) |

## 3. Special Shell Variables

Bash automatically creates certain variables for you the moment it starts — you don't need to assign them yourself. These are sometimes called "free stuff" you get just by using Bash.

### The `UID` Variable

**Example:**
```bash
echo "Your UID is ${UID}"
```

Run the script:
```
chmod 755 luser-demo02.sh
./luser-demo02.sh
```

**Output (example):**
```
Your UID is 1000
```

### Where Does `UID` Come From?

You can find details about it in the Bash manual page.

**Syntax:**
```
man bash
```

Once inside the man page, you can search:

| Key | Action |
|---|---|
| `/searchterm` | Search forward for a word |
| `n` | Go to the next match |
| `N` (Shift+N) | Go to the previous match |
| `?searchterm` | Search backward for a word |
| `q` | Quit the man page |

**Example:**
```
man bash
/UID
```
Press `Enter`, then `n` to move to the next match.

### What the Man Page Says About `UID`

- `UID` expands to the ID of the current user, initialized at shell startup.
- `UID` is a **read-only** variable — you cannot change it.

### `EUID` (Effective User ID)

There is a related variable called `EUID`:

- `EUID` expands to the **effective** user ID of the current user.
- It is also **read-only**.

### Difference Between `UID` and `EUID`

In almost all normal situations, `UID` and `EUID` are the same. They only differ when a script has a special **set UID** permission.

```
Normal script execution:
   UID  = the user who ran the script
   EUID = the user who ran the script
   (same value)

Set UID script (rare, mostly disabled on modern Linux):
   UID  = the user who ran the script  (e.g. 1000)
   EUID = the owner of the script file (e.g. 0 for root)
```

> **Note:** Modern Linux systems block set-UID scripts for security reasons. You may encounter this concept on older or proprietary Unix systems, but on modern Linux, `UID` and `EUID` will always match — so it's safe to just use `UID`.

### Proving `UID` is Read-Only

```
echo $UID
UID=1001
```

The second command will give an error, because you cannot overwrite a read-only variable.

### More Free Variables

Searching `man bash` for the word "shell" (using `?shell` for a backward search) will take you to the **Shell Variables** section, which lists many more variables that Bash automatically sets for you at startup. It's worth reading through this list to see what's available.

## 4. Displaying the Username

### The `id` Command

**Syntax:**
```
id [OPTION]... [USER]
```

> **Reading man page notation:**
> - Square brackets `[ ]` mean the item is **optional**.
> - Three dots `...` (an ellipsis) mean you can repeat that item multiple times.

So `id [OPTION]... [USER]` means: you can run `id` alone with no arguments, or add one or more options, and optionally a specific username.

**Checking what kind of command `id` is:**
```
type -a id
```
This shows that `id` is a **program**, not a shell builtin — so we look it up with `man`, not `help`.

```
man id
```

### Useful Options for `id`

| Option | Meaning |
|---|---|
| `-n` | Print a **name** instead of a number |
| `-u` | Print only the **effective user ID** |

**Example (no options):**
```
id
```
**Output (example):**
```
uid=1000(ayan) gid=1000(ayan) groups=1000(ayan)
```
This shows the UID, the username (`ayan`), the group ID (GID), and the group name.

**Example (just the UID):**
```
id -u
```
**Output:**
```
1000
```

**Example (username only):**
```
id -u -n
```
**Output:**
```
ayan
```

### Combining Single-Character Options

You can combine single-letter options together after one dash. Order does not matter.

```
id -un
id -nu
id -u -n
```
All three of these commands give the same result. The instructor prefers `id -un` (U for "user," N for "name" — easy to remember).

### Alternative: The `whoami` Command

```
whoami
```

Checking its type:
```
type -a whoami
```
This shows `whoami` is a **program**, not a builtin, so check `man whoami` for details.

According to the man page, `whoami` prints the username associated with the current effective user ID — this is the same result as `id -un`.

> **Recommendation:** Use `id -un`, since it's flexible and widely available. `whoami` works too, if you prefer it.

## 5. Storing Command Output in a Variable

You can capture the output of a command and store it inside a variable.

**Syntax (modern style):**
```
VARIABLE_NAME=$(command)
```

**Example:**
```bash
USER_NAME=$(id -un)
echo "Your username is ${USER_NAME}"
```

Save and run the script:
```
Your UID is 1000
Your username is ayan
```

### Older Syntax: Backticks

You may also see an older style using backticks (`` ` ``) instead of `$( )`:

**Syntax (older style):**
```
VARIABLE_NAME=`command`
```

**Example:**
```bash
USER_NAME=`id -un`
```

This does exactly the same thing as `$(id -un)`. It's an older convention — you'll see it in scripts written a while ago, but the `$( )` syntax is the modern, recommended way.

```
Command Substitution — two equivalent styles:

  Modern:  VARIABLE=$(command)     ← preferred
  Older:   VARIABLE=`command`      ← still works, seen in older scripts
```

## 6. The `if` Statement

### Basic Syntax

```
if [[ expression ]]
then
    commands to run if expression is true
else
    commands to run if expression is false
fi
```

**Formatting rules:**
- A space **after** `if`
- A space **after** the opening `[[`
- A space **before** the closing `]]`
- Variables used inside `[[ ]]` should be wrapped in **quotation marks**

**Example:**
```bash
if [[ "${UID}" -eq 0 ]]
then
    echo "You are root"
else
    echo "You are not root"
fi
```

The `if` block always ends with `fi` (which is "if" spelled backward).

### How the `if` Statement Works Internally

**Syntax:**
```
help if
```

The help text explains:
```
if COMMANDS; then COMMANDS; [ elif COMMANDS; then COMMANDS; ]... [ else COMMANDS; ] fi
```

- Square brackets = optional parts (`elif`, `else`)
- `fi` is required to close the statement

### Semicolons vs New Lines

The semicolon (`;`) is a **command separator** — it works exactly like pressing `Enter` to start a new line.

```
Same result:

Style 1 (semicolons, one line):
if [[ "${UID}" -eq 0 ]]; then echo "You are root"; fi

Style 2 (new lines, more readable):
if [[ "${UID}" -eq 0 ]]
then
    echo "You are root"
fi
```

Both styles work. Using new lines is often easier to read, which is why the instructor prefers it.

> **Tip:** If you press `Enter` before finishing a command, your prompt will change to a `>` symbol, showing Bash is waiting for you to finish the command.

### Understanding "True" and "False" in Bash

- An **exit status of 0** means **true** (success).
- Any **non-zero exit status** means **false** (failure).

So the logic is:
```
if (this command's exit status is 0) → then run the "then" block
else                                  → run the "else" block
```

## 7. The Double Bracket `[[ ]]` and the `test` Builtin

### What Are the Double Brackets?

`[[ ]]` is itself a **shell keyword**. You can check its help:

```
help [[
```

It explains that `[[ expression ]]` returns an exit status of `0` (true) or `1` (false), based on evaluating the expression. The expressions use the same building blocks as the `test` builtin.

### The `test` Builtin

```
help test | less
```

`test` evaluates conditional expressions and also returns `0` for true, `1` for false.

### Common Test Operators

**File tests:**

| Operator | Meaning |
|---|---|
| `-a FILE` | True if file exists |
| `-b FILE` | True if file is a block special device |
| `-d FILE` | True if file is a directory |

**String tests:**

| Operator | Meaning |
|---|---|
| `-z STRING` | True if the string is **empty** |
| `-n STRING` | True if the string is **not empty** |
| `=` | Strings are equal |
| `!=` | Strings are not equal |

**Number comparisons (used in our script):**

| Operator | Meaning |
|---|---|
| `-eq` | Equal to |
| `-ne` | Not equal to |
| `-lt` | Less than |
| `-gt` | Greater than |

Our script uses `-eq` to check if `UID` equals `0`:
```bash
if [[ "${UID}" -eq 0 ]]
```

## 8. Testing the Script as Different Users

### Why We Check `UID -eq 0`, Not the Username

The **UID of `0`** is **always** assigned to the **root** user on every Linux/Unix system, without exception. Usernames can vary or be renamed, but UID `0` is guaranteed to always mean root. This makes checking `UID -eq 0` a safe and reliable test.

### Running the Script as a Normal User

```
./luser-demo02.sh
```
**Output (example):**
```
Your UID is 1000
Your username is ayan
You are not root
```

### Running the Script as Root Using `sudo`

**Syntax:**
```
sudo <command>
```
`sudo` stands for **"super user do."** It runs a single command as the root user.

**Example:**
```
sudo ./luser-demo02.sh
```
**Output:**
```
Your UID is 0
Your username is root
You are root
```

### Switching to the Root User with `su`

**Syntax:**
```
su
```

**Example:**
```
su
(enter password when prompted)
./luser-demo02.sh
```
**Output:**
```
Your UID is 0
Your username is root
You are definitely root
```

Type `exit` to leave the root shell and return to your normal user (`ayan`).

## 9. A Note on Portability: Double Brackets vs Single Brackets

- The `[[ ]]` (double bracket) syntax is a **Bash-specific** feature. It will **not** work in every shell (for example, it may fail in `csh`).
- The **older** syntax uses **single brackets** `[ ]`.

**Older style example:**
```bash
if [ "${UID}" -eq 0 ]
then
    echo "You are root"
fi
```

### Interesting Fact: The Single Bracket is Also a File

The single opening bracket `[` is both a shell builtin **and** an actual program file on the filesystem.

```
type -a [
```
This shows it exists as a file (for example, at `/usr/bin/[`). On very minimal shells that don't have `[` built in, the shell will fall back to using this external program instead.

> **Recommendation:** Since we are using Bash, we don't need to worry about this — we'll use the modern **double bracket** `[[ ]]` syntax going forward.

## 10. Sanity Checking (a.k.a. "Idiot Checking")

The kind of check we built in this script — verifying whether the user is root — is sometimes called:

- **Sanity checking**, or
- **"Idiot checking"** (a casual term some people use)

### Why This Matters

If your script requires something specific to work correctly (for example, a script that adds users usually requires root privileges), you should **check for that requirement** in the script itself.

```
Bad practice:
   Assume the user will always run the script correctly.

Good practice:
   Check for requirements (e.g. root access) inside the script,
   and warn or stop if the requirement isn't met.
```

**Why?** Never assume the person running your script knows what's required. They might try to run it as a regular user (like `ayan`) without realizing they need root access. Building in these checks makes your scripts safer and more reliable.

In this tutorial, you learned:

  ```
  if [[ expression ]]
  then

  else

  ```
